# Web

React SPA for Vehicle Vault. Consumes the API over HTTP; owns presentation, forms, client-side query caching, and routing. Shares its domain vocabulary with [apps/api/CONTEXT.md](../api/CONTEXT.md) — use those terms, not synonyms.

## Stack

React 19 + TypeScript + Vite 8. TanStack Router (code-defined routes, not file-based) + TanStack Query 5. react-hook-form + Zod 4 (schemas shared via `@vehicle-vault/shared`). Tailwind 4 (CSS-first: `src/styles/`, no config file) + shadcn/ui (Radix, `style: radix-nova`). Recharts for charts, sonner for toasts, papaparse for CSV import, Vitest (jsdom) for unit tests, Playwright for e2e.

Only env var: `VITE_API_BASE_URL` (`src/lib/env/env.ts`). Throws in PROD build if unset; dev defaults to `http://localhost:3001/api`.

## Language

**Feature slice**:
A self-contained directory under `src/features/<name>/` with the subfolder convention `api/`, `hooks/`, `components/`, `pages/`, `schemas/`, `types/`, `utils/`. All new domain code goes inside a slice, not in shared dirs. Current slices: auth, dashboard, vehicles, maintenance, history, reminders, fuel-logs, loans, accessories, attachments, claims, analytics, vehicle-documents, vehicle-sharing, audit, notifications, admin, settings.

**ApiClient** (`src/lib/api/api-client.ts`):
The single fetch wrapper. Injects `Authorization: Bearer` via a module-level token resolver; on 401 performs one deduped refresh-and-retry, then calls `onUnauthorized`. Configured once by **AuthProvider** via `configureApiClient(...)` — a module singleton, not React context. Never call `fetch` directly.

**Endpoint registry** (`src/lib/api/endpoints.ts`):
Central `as const` map of every backend route the web app calls. Source of truth for the consumed API surface. Never hardcode a path in a feature.

**Query key factory** (`src/lib/query/query-keys.ts`):
Hierarchical `queryKeys.<domain>.<selector>(...)` factory; every key builds on `.all()`. Never inline query keys. (Known violation: the notifications feature uses inline `['notifications']` — treat as debt, not precedent.)

**Format module** (`src/lib/format`):
The only way a value becomes display text: `format.money` (₹, Indian grouping, whole rupees unless asked), `format.number`, `format.distance` / `format.odometer` ("31,800 km"), `format.date` (one style, "23 Sep 2026"; `'short'` "Wed 23 Sep"; `'dateTime'` for when something happened), `format.relativeDue` (`due`: "3 days late" / "Today" / "In 4 days"; `ends`: "153 days left" / "Ended 20 Sep") and `format.enumLabel` (a sentence-case label for every shared enum, via `satisfies Record<Enum, string>` so a new enum value fails the typecheck until labelled). Dates are read on the Indian calendar (fixed UTC+05:30) whatever the browser's zone; a date-only value is UTC midnight, so it keeps its day. Missing or unreadable input prints `format.EMPTY` ("—"), never "Invalid date" or "NaN km". Lint bans `toLocaleString`/`toLocaleDateString`, `new Intl.NumberFormat`/`DateTimeFormat` and date-fns `format` everywhere else in `src`.

**Design tokens** (`src/styles/tokens.css`, spec: [docs/design-language.md](../../docs/design-language.md)):
The "Glovebox folder" look as semantic CSS variables, exposed to Tailwind through `@theme inline` — surfaces (`bg-page`, `bg-surface`), lines (`border-line`), text (`text-fg`, `text-fg-2`, `text-fg-3`), `brand` / `brand-tint`, the statuses `late` / `soon` / `ok` / `ended` with their tints and dots, and the number plate's and tyre's colours. The shadcn names the UI components use (`primary`, `muted-foreground`, `destructive`, `border`, `ring`, …) are mapped onto them, so a screen re-skins by changing a token, not a class. `.dark` holds the dark set (see **Theme**). Type is IBM Plex Sans (body 15, tabular numerals), Anek Latin for `h1`/`h2` and `font-display`, IBM Plex Mono for document numbers, self-hosted from `public/fonts/`; sizes `text-caption` … `text-display` (with `text-ui`, 14, for controls, navigation and dense rows, and `text-field`, 16, for form fields below md so iOS doesn't zoom; Tailwind's own `text-sm`-style sizes are linted out), radii `rounded-control` / `rounded-card` / `rounded-sheet`, and one shadow, `shadow-overlay`, for menus, popovers and sheets. `cn` knows these names (`src/lib/utils.ts`) so tailwind-merge doesn't drop them; `tokens.spec.ts` holds every text pair to WCAG AA. `spacing-utilities.css` keeps `space-y` and `divide-y` working the Tailwind 3 way (the gap on each visible child after the first). A tyre, like the plate, is the same in both themes: `bg-tyre` / `bg-tyre-tread`.

**Design-system guardrails** (`eslint/design-system-plugin.js`, `eslint/design-system-paths.js`):
Lint rules that read every class string (className, `cn`, `cva`, constants) and flag palette colours (`text-slate-500`, `bg-white`), arbitrary font sizes (`text-[11px]`), `transition-all` and any `uppercase` class (tracked or not, any variant), plus `window.confirm` / `prompt`. They are errors on `MIGRATED_PATHS` and warnings everywhere else under `src` (specs excluded), so `pnpm lint` fails only on a migrated area regressing; each migration slice adds its area to that list in the same PR. Uppercase labels are allowed only in the Figure component (`MICRO_LABEL_ALLOWED`); everywhere else the string itself is written in sentence case, mapping data-driven words to labels. Because the web lint lets warnings through, `react-hooks/exhaustive-deps` and unused disable directives are errors.

**Theme** (`src/lib/theme/`, #252):
Light or dark follows the system unless this device picks Light or Dark in the account menu (`useThemePreference`), stored under `vehicle-vault.theme` in `localStorage` (a store that throws reads as System). The inline script in `index.html` puts `.dark`, `color-scheme` and the `theme-color` metas on `<html>` before the first paint, so neither the SPA nor a prerendered catalog page flashes, and it never touches `#root`, so hydration is unaffected; `startThemeSync()` (in `main.tsx`) takes over and follows system changes and other tabs. Keep the script and `theme.ts` in step: `index-html-theme-script.spec.ts` runs the script against `resolveTheme`. Anything rendered at prerender time reads the theme as System/light (`useResolvedTheme`'s server snapshot) and catches up after hydrating; never branch markup on the theme during render. Toasts take their colours from the tokens (`components/ui/sonner.tsx`). The number plate stays white in both.

**Response envelope**:
`{success, data, meta?}` on success; `{success:false, error:{code,message,details?}}` on failure. `api/` functions unwrap `.data`; errors become `ApiError` (carries `status` + body); user-facing text via `getApiErrorMessage()`.

**Search state**:
URL search params validated by a `normalize*Search` function in the feature's `types/`, used as the route's `validateSearch`. Pages are controlled: they receive `searchState` + `onSearchStateChange` (navigate with `replace: true`; defaults stripped from the URL). Examples: `vehicle-list-search.ts`, `history-search.ts`, `vehicle-detail-search.ts` (tab, History view and More section; see **Vehicle page**), `dashboard-search.ts` (attention-queue focus filter; the route re-normalises `useSearch()` output because TanStack's search is non-strict and leaks unknown raw params).

A vehicle with no history and no spend gets **Set up this vehicle** (service, papers, fuel, purchase) instead of the last two; a viewer reads a line instead. The summary card, snapshot tiles, odometer forecast, service trend and the separate service and reminder panels are gone; fuel economy and odometer history stay on the History tab.

**Garage list** (`features/vehicles/pages/vehicles-list-page.tsx`, `components/garage-row.tsx`, #308): one card of rows, each led by the plate and name, then the model and reading, then one status from Home's summary (`vehicleHealthStatus`, joined by id) with the item it is about (`nextDueText`; "Next: …" when all clear) and "Shared · can view/edit" (`ROLE_COPY`); a Show papers link sits beside each row. Sorted by `byUrgency` by default (late, most late items first, then due soon, then all clear, each by how soon; the URL's `sort` still picks another order). Search shows only above six vehicles; bulk delete waits behind "Select" (from two vehicles), which adds a checkbox per row and the bulk bar, and "Done" clears it. The controls card, the attribute cards and the per-card Show papers footer are gone.

**Query-state UI**:
The standard triad `LoadingState` / `EmptyState` / `ErrorState` from `src/components/shared/` for every query-backed view. Forms use `FormField`; mutation errors go to `appToast.error(getApiErrorMessage(e))`.

**Resource load error** (`components/errors/resource-load-error.tsx`): what a single-resource detail page (`VehicleDetailPage`, `MaintenanceRecordDetailPage`, `ReminderDetailPage`) renders for its `query.isError` branch — a 404 reads as "isn't in your garage" (the id was malformed or unknown, never a 500), a 403 as access having been removed, and anything else as retryable, with a `Try again` that calls the query's own `refetch`. One component owns the three messages so the pages don't restate and drift on them.

**Vehicle naming**:
`describeVehicleModel(vehicle)` builds the "make model variant" line everywhere one is shown. The variant is optional on a vehicle, so the helper drops it rather than leaving a separator with nothing after it; About this vehicle says so outright, because specs are published per variant and its lookup never runs without one.

**Vehicle page** (`features/vehicles/pages/vehicle-detail-page.tsx`, `components/vehicle-detail-header.tsx`, `vehicle-tab-list.tsx`, `vehicle-more-tab.tsx`, `types/vehicle-detail-search.ts`):
An identity header, then five tabs that fit a 390px phone without scrolling: Overview, History (the service log or the fuel log through a Service / Fuel control, `?view=fuel`, with the odometer readings), Reminders (with the suggested service schedule), Papers (every paper and claim) and More (a list of About this vehicle, Tyres, Accessories, Loans for the owner, Members and Activity, each opened on its own as `?section=` by a link so Back returns to the list, then the downloads, Edit vehicle and the owner's Delete vehicle). The header is the L plate, the name, the model line with the odometer and when it was last updated, then Show papers (the first of insurance, PUC, RC and road tax on file, full screen, else the Papers tab), Log ▾ (service opens the full form; fuel, odometer and paper open the same dialogs as **Quick log**; reminder; `canEdit` only) and a more menu with the same downloads and edits. Papers carries a dot when a paper has expired or runs out within 30 days (`papersAttention`, which reads each kind's document of record and ignores an ended warranty), named in words for a screen reader. The page had eleven tabs until #276; `legacyVehicleDetailTabs` maps each old `?tab=` value to its new home, `validateSearch` applies it and the route's `beforeLoad` rewrites the address, so alerts already sent and the API's notification links (which still write the old values) keep working.

**Vehicle access** (`features/vehicles/context/vehicle-access.tsx`):
The signed-in user's role on the vehicle on screen, provided from `vehicle.currentUserRole` by every vehicle-scoped page: `VehicleDetailPage` (where the members lookup is a fallback), the maintenance-record and reminder detail and edit pages, the maintenance and reminder create pages, and `VehicleEditPage`. A page that only learns its vehicle from a record it is loading gets the role from `useVehicle(record.vehicleId)`, which waits on an empty id. Anything nested reads `useVehicleAccess()`: `canEdit` (owner or editor) gates every create/edit/delete/import/scan control, `isOwner` gates deleting the vehicle, loans and member management. Viewers get the same lists, details and downloads with the controls removed, not disabled, and a "View only" badge on the vehicle header explains why; a form a viewer cannot submit is replaced by `ViewOnlyNotice` rather than left to 403 on save. Outside the provider nothing is hidden (`canEdit` defaults to true) — the API is the enforcement, this only avoids offering a button that will 403. Cards that take optional `onEdit`/`onDelete`/`onSelectionChange` handlers drop their controls when the handler is omitted; cards that always render a delete read the context themselves.

**Draft confirmation** (`features/maintenance/pages/maintenance-record-edit-page.tsx`):
A record the upload-first flow made (`status: draft`, `source: ocr`, filled from its bill as part of that flow; see **Upload-first prefill**) is an extraction nobody has agreed to, and everything in the API that answers what was done or spent reads confirmed rows only. Its edit page is where a human agrees, so for a draft the page is titled "Confirm Maintenance Record", the form's button reads **Confirm Record**, and the save sends `status: 'confirmed'` beside the reviewed fields — one PATCH that saves the edit and confirms, which is what fires `first_maintenance_logged` and the next-due reminder in the API's `updateRecord`. Saving a draft always confirms it; there is no "save but leave it a draft" path, because a record left a draft stays out of every cost, report and reminder, and this page, where each **History page** (`/history`, `features/history/`):
The garage's timeline from the API's `GET /history`: service records, fuel fills and odometer readings, newest first, grouped by month with the month's confirmed spend in its header ("Spent ₹7,200 · 1 draft not counted"). Each row is one `HistoryRow`: the S plate (hidden in a one-vehicle garage), what with an icon, when · where · odometer, and the amount; a service opens its record, a fill the vehicle's fuel log, a reading the vehicle. The vehicle and kind filters are the URL's `vehicle` and `kind` (`normalizeHistorySearch` drops anything else, including the old list's `category` and `sort`); "Show older entries" loads the next page (`useHistory`, an infinite query). Its query key sits under `audit.all()`, since every write it shows is audited and already invalidates that.

**History summary and phone layout** (#310): under the H1 one line, "₹15,200 on 3 services in 2026 · 1 draft to confirm →", from the API page's `year` (this calendar year's confirmed services under the vehicle filter; null when the kind filter leaves services out, and the plain description shows instead) and `firstDraftId` (the draft waiting longest, which the link opens). **Upload-first prefill** (`features/maintenance/pages/vehicle-maintenance-create-page.tsx`, `components/draft-bill-summary.tsx`, `utils/get-fields-from-bill.ts`):
"Snap the bill" (the camera) or "Choose file" (a photo already on the phone, or a PDF) creates a draft, uploads the files, reads them (one file alone, several pages together) and, when the read found anything, applies it to that draft before opening its confirm page, so the form opens filled in rather than blank behind "Apply to Draft". Apply is only ever called on the draft the flow made a moment ago, and the API refuses it on a confirmed record, so this path never touches a confirmed record; nothing counts until **Confirm Record** (see **Draft confirmation**). The confirm page shows the bill's thumbnail and one line saying what reading it gave: filled in, nothing readable, the read failed (with its reason), reading unavailable, or read but not applied. Each form field that still holds what the bill says carries a "from bill" marker until it is edited; which fields those are is worked out from the draft's saved values against the latest completed read, not remembered from the upload, so a reload keeps the markers. Document Review keeps "Read again" and "Apply to Draft" for retries.

**Log service form** (`features/maintenance/components/maintenance-form.tsx`, `pages/vehicle-maintenance-create-page.tsx`, #293): the approved "Log service" board, one short screen on a phone, in this order: the bill buttons (new record only, see **Upload-first prefill**), "What was done" as one-tap chips (Oil change, Periodic service, Brakes, Tyres, Battery, More… for every other category), Date and Odometer defaulted to today and the vehicle's reading with one line saying so (#203's checks unchanged), "Total on the bill" (empty, required, grouped the Indian way as it is typed by `AmountInput`), the extras collapsed (Workshop with the owner's past workshops from `GET /maintenance-records/workshops` one tap away, Parts and labour with the line-item editor, which then works the total out, and Notes), the next due, and "Save service", 52px and pinned above the phone's bottom bar. The next due is worked out before saving from the vehicle's resolved interval for that work (`GET /vehicles/:id/intervals`, the numbers the alert and forecast engines use) counted from this service's date and reading, and saved as the record's `nextDueDate`/`nextDueOdometer`, which the API turns into the reminder, so the preview is what gets scheduled; a later service of the same kind, or a next due already reached, sets none. This applies to a new record and a draft; a record's own next due (the bill's, or an earlier save) is kept and marked, and Change edits it. The edit and confirm pages use the same form.

**New-record address** (`features/maintenance/types/maintenance-create-search.ts`, #293): `/vehicles/:vehicleId/maintenance/new?category=<slug>&reminderId=<id>` is a contract other flows link to (a reminder's Done → Log service, #295). `category` is a maintenance category as the API names it (`engine_oil`, `periodic_service`) and preselects it; `reminderId` (a UUID) names the reminder the service is logged for, shown under the chips ("For your reminder “Engine oil due”."), and when `category` is absent its work picks the category. Either wins over the due-reminder pick. `normalizeMaintenanceCreateSearch` drops an unknown category, a malformed id and anything else; a reminder of another vehicle is ignored. Saving sends it with the record, which completes the reminder (see **Logging for a reminder**).

**Logging for a reminder** (`hooks/use-linked-reminder.ts`, `types/maintenance-create-search.ts`): a service logged from a reminder's "Log the service now" sends its `reminderId`, and the API completes the reminder with the record. When the reminder repeats, its own rule, not the schedule, sets the next one (the reminder page promises it is "counted from the service you log"): the form shows that next due and sends none, so the API schedules the reminder's next occurrence with its title and rule; a next due the owner types, or the bill's, still wins. "Snap the bill" from such a form opens the draft's confirm page with `?reminderId=` (`normalizeMaintenanceEditSearch`), which says confirming completes the reminder and sends the id with the confirm; an edit of a confirmed record never completes one.

**Verification grace**:
An unverified account gets the whole app for a week, then a wall. The API decides the deadline and sends it as `user.emailVerificationDueAt` (null when there is nothing to verify: verified, or an OAuth account with no address); `getVerificationStatus()` (`features/auth/lib/verification-status.ts`) only compares it with the clock. Inside the week `AppLayout` shows `EmailVerificationBanner` (days left, resend, dismissed until the next local day per user); after it, `EmailVerificationScreen` replaces the app. A session from an API that sends no deadline at all keeps the wall. The verification link usually opens in a new tab: there `/verify-email` refreshes the signed-in user (`refreshUser()` on the auth context) and returns to `/home` rather than to login, and the original tab re-reads the account when it comes back into view. Both surfaces resend through `useResendVerification`, which holds a 60-second cooldown on top of the API's `mail` rate limit.

Emailed links (verification, password reset) fail out loud and never touch the session. `verifyEmail` skips the refresh and the unauthorized handler, so a spent or unknown link (the API's 401) shows "This link has expired or was already used" with Send a new link (signed in) or Sign in (signed out) instead of signing anybody out; a signed-in account that is already verified is told so without spending the link; a link with no token is "incomplete"; any other failure offers Try again. The reset page reads its token from the address only (no field), and a missing or refused token replaces the form with Request a new link. Forgot-password swaps the form for a panel that stays (address, 30-minute life, Send again after 60 s, Use a different email), or, when the API answers 503 because no mail transport is configured, says reset by email is not available yet. Resend verification reports `delivered: false` when the server cannot send mail, and the UI says no link went out rather than "sent".

## Routing

Route tree assembled in `src/app/router/index.tsx`; one `*-route.tsx` file per route under `src/routes/`, barrel-exported from `routes/index.ts`. Pages are code-split via `createLazyPage` (`lazy-page.tsx`).

- Public: `/`, login, register, forgot/reset-password, verify-email, oauth-callback.
- `appRoute` (id `app`) guards everything else: `beforeLoad` redirects unauthenticated users to `/login`. Admin routes additionally check `auth.user?.role === 'admin'`.
- Return path (`next`): the guard's redirect carries the address the visitor was opening as `/login?next=<path>` (only when the route is being entered: signing out on a page re-runs the guard with `cause: 'stay'` and lands on a plain `/login`), and a session that expires mid-use does the same (`loginHrefReturningTo`). `/login` and `/register` keep it (their "Create one" / "Sign in" switch passes it on, and dropping the `catalog` parameter leaves it), the Google/GitHub buttons send it to the API, which signs it into the OAuth state and hands it back in the callback fragment, and every one of them ends at `afterAuthDestination` (`features/auth/lib/return-path.ts`): the return path, else the catalog intent's `/vehicles/new`, else `/home`. Only same-origin paths survive (`toSafeReturnPath` in the shared package, applied in `validateSearch`, in the OAuth state both ways, and again on the callback): no scheme, no `//` or backslash, no whitespace or control characters, no dot segments, and none of the signed-out auth pages.
- Invite links (`/vehicle-invites/$token`) are public, outside the app shell, in the auth layout: the page previews the invite and never accepts on its own. Signed out it offers Sign in / Create account to accept, both carrying `next` back to the invite; signed in to the invited account, Accept (on to the vehicle) and Decline; signed in to another account, it names both addresses and offers Sign out and switch account (a `flushSync` logout, then `/login?next=`). After inviting, the Members tab shows the link with Copy, WhatsApp and the native share sheet, and says an email went out only when the API's `emailSent` is true.
- `ROLE_COPY` (`features/vehicle-sharing/lib/role-copy.ts`) is the one place role names and their plain-word descriptions live, so the invite dialog, the Members list and the invite preview page all say the same thing about what a viewer or editor can do; the invite dialog also names the owner-only actions (invite, change roles, remove, transfer ownership) directly. The share sheet, where the browser offers one, leads the invite-link buttons, then WhatsApp, then Copy link — updated from the Copy-first order `Invite links` above still describes. A pending invite's token is never re-readable (only its hash is stored), so "copy it again" calls `POST vehicles/:id/invites/:inviteId/resend`, which rotates the token, tries mail again exactly like creating the invite, and invalidates whatever link was handed out before.
- Data loading is entirely in-component via TanStack Query — no router `loader`s. `defaultErrorComponent` and `defaultNotFoundComponent` are set on the router (see Testing → Errors and unknown addresses). `defaultPreload: 'intent'`.

Adding a route: create `routes/x-route.tsx` → export from `routes/index.ts` → wire into the tree in `app/router/index.tsx`.

## Data layer conventions

- `api/*.ts` exports an async function hitting `apiClient` and usually a `*QueryOptions()` factory. Hooks are thin `useQuery(xQueryOptions())` / `useMutation` wrappers.
- Query client defaults: `staleTime` 60s, `gcTime` 5min, no refetch-on-focus, queries `retry: 1`, mutations `retry: 0`.
- Mutation `onSuccess`: invalidate the domain's `queryKeys.<domain>.all()` (+ dashboard where relevant) and call `invalidateAudit(queryClient)` for audited writes.
- Domain types and Zod schemas come from `@vehicle-vault/shared` — feature `types/` and `schemas/` mostly re-export. Don't duplicate.
- Blob downloads (service-history PDF, resale report, account export) go through `apiClient.getBlob` — a separate code path from JSON.

## Auth

`AuthProvider` (`features/auth/providers/auth-provider.tsx`) owns token lifecycle: localStorage persistence (`vehicle-vault.auth-session`), silent refresh, expiry timer. Session expiry / refresh failure hard-redirects via `window.location.replace('/login')`, bypassing the router.
