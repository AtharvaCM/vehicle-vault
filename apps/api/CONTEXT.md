# API

NestJS backend for vehicle-vault. Owns the persistence model and business rules for vehicles and everything attached to them.

## Architecture facts

- NestJS 10, PostgreSQL via Prisma, ~22 modules under `src/modules/`. Global route prefix `api`; Swagger at `/api/docs`.
- **Every route is auth-protected by default** — `JwtAuthGuard` is a global `APP_GUARD` (registered in `AuthModule`); opt out with `@Public()`. Role gates via `@Roles(...)` + `RolesGuard`; per-vehicle access via **VehicleAccessService**.
- Global `ApiResponseInterceptor` wraps responses in `{success, data}` (binary/stream responses excluded); `GlobalExceptionFilter` produces `{success:false, error, meta}`.
- Validation is **mixed**: class-validator DTOs dominate (~42), with a minority of Zod DTOs using `ZodSchemaValidationPipe` + schemas from `@vehicle-vault/shared`. Not unified — known debt.
- Cron via `@nestjs/schedule`; the alert engine runs `MAINTENANCE_ALERT_CRON` (default `0 6 * * *`), **disabled when `NODE_ENV=development`**.
- **RLS**: enabled deny-by-default with no policies on all public tables. Intentional — the app connects as `postgres` (bypasses RLS); RLS only closes Supabase PostgREST exposure. No client-side RLS model exists.
- Storage: `SupabaseStorageService` with dual backend (Supabase Storage or local FS via `attachmentStorageBackend` — local used in CI).
- Config: `AppConfigService` typed wrapper. Note: JWT secrets have dev fallbacks with no prod startup assertion.
- Tests: Vitest, co-located `*.spec.ts` unit tests; no API-level e2e harness (web Playwright smoke covers it).
- Every `:id`-style route param backed by a UUID primary key 404s on a malformed value, matching the 404 an unknown-but-valid id already gets, instead of the 400 a plain validation failure would give or the 500 an invalid `uuid` literal throws from Postgres: DTO-shaped params (`@Param() params: XyzDto`) use the `@IsUuidRouteParam()` validator (`common/validators/is-uuid-route-param.validator.ts`), which `AppValidationPipe` (`common/pipes/app-validation.pipe.ts`, wired in `main.ts`) remaps from 400 to 404; bare scalar params use `UuidRouteParamPipe` (`common/pipes/uuid-route-param.pipe.ts`) directly on `@Param('x', ...)`. Non-UUID route params (catalog slugs, document `kind`, OAuth `provider`) are untouched.

## Language

**Vehicle**:
A car or two-wheeler in a **User**'s garage. Root of most aggregates. Ownership is expressed through **VehicleMember** rows; `Vehicle.userId` survives as a legacy owner FK (still carries the `[userId, registrationNumber]` unique and cascade) — queries go through `members.some`, so **VehicleMember is authoritative**. A Vehicle may link to a **CatalogVariant** (`catalogVariantId`, fuzzy-matched by `VehicleCatalogLinkerService`). `Vehicle.odometer` has two writers with different rules: `PATCH /vehicles/:id/odometer` (the dashboard's quick update) only moves it forward and refuses a lower reading, while the full vehicle update may lower it, since that form is where a mistyped reading gets corrected. Fuel logs also raise it, never lower it.

**VehicleMember** / **VehicleRole**:
A **User**'s role on a **Vehicle**: `owner`, `editor`, or `viewer` (ranked). Enforced everywhere by **VehicleAccessService** (`assert`/`assertEditor`/`assertOwner`; throws NotFound to prevent id probing). Sharing happens via **VehicleInvite** (hashed token, expiry, accept/revoke) and ownership transfer.

**Vehicle invite**:
How an owner shares a **Vehicle**: an invite for an email address and a role, reached through a link carrying a random token (only its hash is stored), valid 7 days. `createInvite` always returns the link (`acceptUrl`) and says whether an email actually went out (`emailSent`), since mail may not be configured and families forward links anyway. Anyone holding the link can preview it (`POST /vehicle-invites/preview`, public: vehicle label, inviter, role, the address masked as `r***@gmail.com`, expiry, status); signed in, `POST /vehicle-invites/preview/mine` adds `addressedToYou`. Only the invited account can accept or decline (`decline` sets `declinedAt`, which ends the invite like `acceptedAt` and `revokedAt`, is audited as `vehicle_invite.declined` for the owner, and does not block a fresh invite). The token travels in request bodies, never in API paths or queries.

**VehicleDocument**:
A time-bounded record of coverage or registration on a **Vehicle**. Has a provider, a validity window (`startDate`–`endDate`), and a `kind`: `insurance`, `warranty`, `registration`, `puc`, `road_tax`. For insurance and the compliance kinds the expiry is the only field required: the provider, the number and `startDate` are all nullable, so a record may exist knowing nothing but when it runs out — which is what the **vehicle setup prompt** collects. A warranty still needs its provider and start date. Unified behind one service via per-kind adapters (`VEHICLE_DOCUMENT_ADAPTERS` DI multi-provider). Insurance and warranty persist in dedicated tables (`InsurancePolicy`, `Warranty`); the three **compliance kinds** (registration certificate, PUC, road tax) share one `ComplianceDocument` table discriminated by kind, since their field shape is identical (issuing authority, number, validity window, amount). A null `endDate` means never expires (e.g. lifetime road tax); a null `startDate` means the start was never recorded, and ranks below any dated document when picking the one of record (`document-recency.ts`). See ADR-0001.
_Avoid_: Policy (insurance-only), Coverage (warranty-only).

**Document files**:
Every **VehicleDocument** keeps its own files: `Attachment` rows with `insurancePolicyId`, `warrantyId` or, for the three compliance kinds, `complianceDocumentId` set. The CHECK constraint `attachment_owner_exclusive` still allows exactly one owner per row. They are served at `GET|POST /vehicle-documents/:kind/:documentId/attachments`. A compliance record answers only to its own kind, so a PUC can't be reached as a registration. Files follow the vehicle's access: any member may list and open them, only an editor may upload or remove. Size and type limits are the shared attachment rules. They are stored under the uploader's prefix `attachments/<userId>/<documentId>/`. Deleting the document reads its file paths first, lets the cascade drop the rows, then removes the files best-effort. Deleting a vehicle removes the files of all its documents and loans as well as its maintenance records.

**Fuel economy**:
What a **Vehicle** actually returns, measured fill to fill from its fuel logs (`vehicles/fuel-economy.ts`, served at `GET /vehicles/:id/fuel-economy`). The figure is the distance from the first usable fill to the last, over the fuel bought after the first. The logs have no full-tank flag, so a partial fill skews a single interval but evens out across a run. For the same reason one fill never gives a number. A usable fill has fuel in it and an odometer reading past the previous fill; a reading of 0 means it was not recorded. The unit follows the fuel type: km/L, km/kg for CNG, km/kWh for electric. The claimed figure is `CatalogVariantSpec.mileageCombined` of the variant the vehicle is linked to, shown only in the same unit, so an EV (whose catalog figure is a range) shows none.

**History timeline** (`modules/history/history.service.ts`, `GET /history`):
The garage's record of what was done, newest first, across every vehicle the user can see (or one, with `vehicleId`; `kind` narrows to `service`, `fuel` or `odometer`). It merges three sources: **MaintenanceRecords** (drafts included, marked by `status`), **FuelLogs**, and odometer readings. A reading has no table: each `vehicle.updated` **AuditEvent** whose `changedFields` include `odometer` (the odometer update and the edit form) is one, with the reading before and after; a fill moves the odometer without such an event, so it is never listed twice. Pages are keyset-paginated over (time, id) with an opaque cursor, reading each source for one row past the page. `months[]` gives each month on the page its confirmed service and fuel spend over the whole month under the same filters (drafts never count; null when nothing can), so a month split across pages keeps one total. Months are Indian calendar months, as the web shows dates.

**Vehicle setup prompt**:
The two-date question a newly created **Vehicle** lands on: insurance expiry and PUC expiry, or insurance alone for an electric vehicle (**PUC exemption**). Answering either creates a **VehicleDocument** of that kind carrying nothing but the expiry, so the expiry alerts start the minute the vehicle exists. `Vehicle.setupPromptDismissedAt` records that it was answered or skipped, and `POST /vehicles/:id/setup-prompt/dismiss` (editor) sets it once — unaudited, like a dashboard snooze, since it records a question being asked rather than a change to the vehicle.
_Avoid_: onboarding wizard (there is no multi-step flow).

**PUC exemption**:
A PUC (Pollution Under Control) certificate is legally required of every **Vehicle** that burns fuel, hybrids included. An electric vehicle is exempt, so nothing asks it for one: the dashboard reports no `puc` status for it rather than `missing`, the data score skips the check, the **vehicle setup prompt** asks for insurance alone, the resale report marks the PUC not applicable, and the service schedule does not offer a PUC renewal. The rule is `requiresPuc(fuelType)` in `@vehicle-vault/shared`; the schedule predates it and lists its fuels itself. A PUC that is on file is still tracked like any other **VehicleDocument**, expiry alerts included.

**MaintenanceRecord**:
A single completed service visit. Has line items, costs, odometer, `status` (draft/confirmed), optional extraction-backed attachment, optional 1:1 **Claim** link. **Not** a **VehicleDocument** — different shape (line items, currency math) and different behaviour (forecasting, extraction ingestion). See ADR-0001.

**Fill in from photo**:
How a confirmed **MaintenanceRecord** takes what a **DocumentExtraction** read off one of its own attachments — usually the job card a quick log attached, which the decision on #116 says is never read unasked. `GET /attachments/:attachmentId/fill` says what it would write and `POST` writes it; both need an editor and an extraction that has finished, since reading the file is its own request. It writes only fields the record leaves blank or at the quick log's default: category `other` (from the first line item that names another), workshop, invoice number, notes, line items, and the next-due date and odometer. Never the date, odometer, cost, currency, status or source (`attachments/maintenance-fill.ts`). Line items go in only when they add up to the record's cost: the web edit form works a record's cost out from its line items, so any others would replace the typed cost at the next save. A next-due at or before the service is dropped as this visit, misread. The write is an ordinary `MaintenanceService.updateRecord`, so it is audited as `maintenance.updated` in its transaction, and a next-due it adds makes the record's reminder. `AttachmentsService.applyExtraction`, which writes the whole extraction and leaves the record a draft, refuses a confirmed record.

**Accessory**:
Something bought for a **Vehicle** and optionally fitted to it — mats, a dashcam, alloys. Has a purchase date and cost, an optional fitted/removed lifecycle (`removedDate` null with a `fittedDate` present means currently fitted), and an optional `warrantyExpiresAt` that the **AlertEngine** treats like a document expiry. **Not** a **MaintenanceRecord**: a purchase has no service date and no odometer reading at time of service, and counting it as maintenance corrupts the ₹/km figure maintenance history exists to produce. Its `category` is free text on purpose — a premature enum is what pushed accessories into `MaintenanceCategory` before this table existed. Not transferable between vehicles.
_Avoid_: part (a **MaintenanceLineItem** kind), upgrade, mod.

**Claim**:
An insurance claim on a **Vehicle**, tied to an **InsurancePolicy**, optionally linked 1:1 to the **MaintenanceRecord** that repaired the damage. Has its own attachments and extraction kind.

**VehicleLoan**:
A financing record on a **Vehicle**: amortization schedule (EMI math in `vehicle-loans/amortization.ts`), prepayments, foreclosure, attachments, and its own extraction kind (`loan_document`).

**Reminder**:
A future-dated to-do tied to a **Vehicle**, timed by `dueDate`, `dueOdometer`, or both. Drives both UI surfaces and the alert engine. Service-schedule suggestions come from `ServiceScheduleService` + `service-schedule-catalog.ts`. A confirmed **MaintenanceRecord** carrying `nextDueDate`/`nextDueOdometer` (what the workshop wrote down, usually captured by the extractor) makes a reminder of its own. The reminder is linked back by the unique `Reminder.sourceMaintenanceRecordId` (set null if the record is deleted) and synced by `maintenance/next-due-reminder.ts` inside the record's transaction:

- re-confirming or editing the record refreshes that reminder, unless it was completed;
- a record with neither field makes nothing;
- a newer confirmed service of the same category completes the record-made reminders older services left open (never manual ones);
- an import takes only the newest record per category.
  Status comes from `reminders/reminder-status.ts`, the rule the reminders service uses.

Both timings alert. The **AlertEngine** judges each one it has — an odometer mark within 500 km, a due date within 7 days — and raises at most one **Notification** per reminder per run, overdue winning over due: a reminder carrying both is one task and should arrive once. Days are counted as whole UTC calendar days, the same arithmetic `RemindersService` uses to derive `ReminderStatus`, so a notification cannot contradict the status shown on the row it came from; due _today_ is due, not overdue. The two alert kinds render date copy or kilometre copy from the basis the engine chose (`ReminderAlertBasis`), never both — a date-only reminder has no kilometres to quote, and inventing them from the mileage forecast is what the engine refuses to do elsewhere.

A reminder **repeats** when it has a **repeat rule**: `Reminder.repeatEveryMonths` and/or `repeatEveryKm`, whichever comes first when both are set; both null means it does not repeat. Completing one schedules the next occurrence (`ServiceScheduleService.buildNextOccurrence`, date arithmetic in `reminders/repeat-rule.ts`): counted from completion (now, current odometer), except that a renewal (insurance, PUC, tax) completed early keeps its cycle and counts from its due date, and the tyre walk-around counts from the last tyre reading. The owner sets the rule on the reminder form; a reminder made from the suggested schedule gets its item's interval as its rule and records its origin in `Reminder.catalogSlug`, which also drives the schedule's duplicate checks and the **AlertEngine**'s tyre walk-around skip. A schedule reminder whose item no longer applies to the vehicle, or whose item another open reminder already covers, is not repeated. A successor that would be born already due on every limit it has is not created at all: it would repeat what the completed row said, and completing that one would produce another. The columns carry nothing reminder-specific, so a document expiry can follow the same rule. (Until migration `20260923220000_reminder_repeat_rule`, origin lived in a `[catalog:<slug>]` marker appended to `notes`; the migration moved it into the columns and cleaned the notes.)

**Renewal** (`reminders/renewal-link.ts`, #283):
A **Reminder** of a renewal type (`insurance`, `puc`, `tax`, `registration`: `RENEWAL_DOCUMENT_KIND_BY_REMINDER_TYPE`) follows the vehicle's **VehicleDocument** of the matching kind through `Reminder.insurancePolicyId` or `Reminder.complianceDocumentId` (at most one, checked; unique, so a paper has one renewal; `SET NULL` on delete). While linked, its due date is the paper's end date: every paper write re-dates it (`VehicleDocumentsService` → `syncRenewals`), reads take the date from the paper, the reminder's own date can't be edited, and it can't be snoozed (snooze the paper instead). When a newer paper of the kind becomes the one of record (Renew), the linked reminder is completed and a successor with the same title, notes and repeat rule follows the new paper. Deleting the paper leaves a plain reminder, dated where the paper ended. A paper with nothing following it adopts the vehicle's one open, unlinked reminder of its kind when that reminder is due within 60 days of the paper's end (or has no date). Two candidates, or one further off, is ambiguous and left alone. A new renewal reminder links to the paper of record when nothing open follows it yet. Changing a linked reminder's type away from the paper's kind unlinks it. A paper and the reminder that follows it are one row on Home and Upcoming (the paper's row, under the reminder's title, carrying `reminderId`). The **AlertEngine** skips linked reminders, so the paper's own expiry alert is the renewal's only notification. Migration `20260925120000_reminder_follows_paper` applied the adopt rule to stored rows, after deleting exact duplicates (open renewal reminders equal on every field someone could set, oldest kept).
_Avoid_: tracking a renewal twice (a paper plus an unlinked reminder for the same expiry).

**Reminder handoff** (`RemindersService.prepareCompletionByRecord` / `completeByRecord`, #295):
A service record saved with `reminderId` (the log-service form's `?reminderId=`, sent in the create or update body and never stored) completes that **Reminder** in the record's own transaction, once the record is confirmed: a draft leaves it open until it is confirmed. The next occurrence is counted from the record's service date and odometer rather than from now (`buildNextOccurrence`'s `from` anchor; a future date counts from today). When the record carries its own next-due, the reminder that makes is the next one: no second is scheduled from the rule, and that reminder takes the completed one's repeat rule and catalog slug instead. A reminder already complete is left alone, one on another vehicle is refused (400), and the bell is cleared for it as a plain completion does. Each reminder carries `logCategory`, the category such a record takes (the record that set it, then its schedule item, then its type: service, tyre rotation, battery); none for a renewal that follows a paper, a check or a custom to-do, which the web simply marks done.

**Reminder snooze** (`PATCH /reminders/:id/snooze`, `reminderSnoozeTarget` in `@vehicle-vault/shared`, #295):
The body picks how far: `{ period: 'week' | 'month' }` or `{ until: 'YYYY-MM-DD' }`, a week when empty. Counted from the reminder's date while that is ahead, otherwise from today; a picked day must be after that (400 otherwise), so a snooze never brings a reminder closer. Kilometres move from the odometer or the target, whichever is further, by 500 km per started week of the same span (a week 500, a month 2,000–2,500). The web previews with the same shared function, so its preview is what the API writes. A renewal that follows a paper still cannot be snoozed.

**Schedule anchor**:
What a proposed interval is counted from: the last time the item was done, else "now, at the current odometer". A catalog item with a maintenance category resolves its latest confirmed **MaintenanceRecord** of that category (highest odometer, as the baseline coverage and the **AlertEngine** read it), then the owner's known **ServiceBaseline** answer, then now; drafts never anchor. The tyre walk-around anchors on the last **tyre observation**, so scheduling a check 4 000 km after the last one proposes it in 1 000 km rather than 5 000. An anchor never runs ahead of today or the vehicle's odometer. Anchors are per-slug and resolved once, so previewing a suggestion and applying it produce the same reminder, and each suggestion carries its anchor so the row can say "Last done … → next …" or "No history — counted from today". Completing a catalog reminder counts its successor from the completion, except the walk-around, whose completion is not a measurement.

**Upcoming timeline** (`GET /upcoming`, `dashboard/due-items.ts`):
Everything with a date across a user's vehicles — open **Reminder**s, the latest **VehicleDocument** per kind, each active **VehicleLoan**'s next EMI, the **AlertEngine**'s tyre and service-history verdicts, accessory warranties — classified once by `buildDueItems` into `overdue` · `today` · `this_week` · `this_month` · `later`. Home's attention queue is that list minus `later` (`isAttentionItem`), read by `DashboardService` from the same sources in the same request shape, so Home and Upcoming cannot disagree about what is late or due this week (`upcoming.spec.ts` holds them together on the demo seed's shape). `later` is what Home leaves out: dated beyond 30 days, an odometer-only reminder more than 1 000 km away, an EMI more than seven days off (an instalment is routine until its week), and a paper the user snoozed off Home while it is not yet due (it carries `snoozedUntil`; a paper that has come due ignores the snooze). A paper and its linked **Renewal** reminder are one row. A paper that ran out more than 90 days ago and a completed reminder are on neither. The page groups `today` with `this_week`. Filters: `vehicleId`, `kind` (`reminders` · `papers` · `emis` · `other`); `page`/`limit` page the `later` group only, so the near groups always arrive whole. Ties sort by title, then vehicle name. `PATCH /reminders/:id/snooze` is the reminder's "not now": a week on from today (or from its date if later) and, where it counts kilometres, 500 km on from the odometer or its target; an editor action, audited as an update, and it clears the reminder's bell.

**Notification**:
A user-facing message persisted per **User** with a `kind` and a `dedupKey`. Uniqueness for unread notifications enforced by partial unique index on `(userId, dedupKey) WHERE isRead = false`; a dedup collision returns the existing unread row rather than throwing. See ADR-0003. Deleting one is a hard delete, so no cooldown reads these rows — see **AlertRaise**.

**AlertKind**:
A typed alert category — `maintenance-due`, `maintenance-overdue`, `reminder-due`, `reminder-overdue`, `document-expiring`, `accessory-warranty-expiring`, `tyre-worn`, `tyre-aged`, `tyre-uninspected`, `service-baseline-unknown`. Enumerated at runtime as `ALERT_KINDS` so a kind with no registered template fails a test rather than a cron run. Each kind has an **AlertTemplate** that owns content rendering and `dedupKey` computation.

**AlertTemplate**:
The per-**AlertKind** producer of notification content (title, message, link, urgency) and dedup identity. Wired via `ALERT_TEMPLATES` DI multi-provider behind **NotifyService**. A title that prefixes fixed wording onto user-supplied text builds it with `prefixedTitle` from `templates/notification-title.ts`: `Notification.title` is VARCHAR(120) and the interpolated value can fill that on its own, so an untrimmed title throws on insert — and `runDailyChecks` catches per vehicle, losing that vehicle's remaining alerts for the run. `message` is TEXT and carries the value whole.

**Channel**:
An external delivery adapter for a **Notification** (`email` and `push` today; `sms` future). The DB row is the canonical record; channels are out-of-band fan-out (`Promise.allSettled`, failures logged not thrown). Push is web-push/VAPID (`PushSubscriptionsService`, gated on `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`); one **PushSubscription** row per browser endpoint, pruned automatically on 404/410.

**Alert email gate**:
Alert mail is the one thing this app sends in bulk, and `EmailChannel` withholds it in three cases: an address nobody has verified (`User.emailVerified`), a user who has silenced it (`User.alertEmailsMutedAt`), and a missing `API_PUBLIC_URL`, which would mean mailing an unsubscribe link that leads nowhere. Each one fails closed and none of them touches the **Notification** row or the push Channel — an alert the user should not be emailed is still an alert, and hiding the record would hide the thing from the person who asked to be told about it.

The opt-out is a stateless HMAC token (`UnsubscribeTokenService`) carried both in the mail body and in `List-Unsubscribe` / `List-Unsubscribe-Post` (RFC 2369 and RFC 8058 one-click). Stateless rather than a row like the password-reset token because the link must still work in a year-old email; there is nothing to revoke, since the token can only ever reduce what we send. `UnsubscribeController` serves it unauthenticated at `/notifications/unsubscribe` — HTML for a browser on GET, an empty 200 for the mail client on POST — and is the only endpoint in the API that returns a page. `AlertEmailPreferenceService.mute` is what the link calls; it writes an **AuditEvent** with a null actor, because the token proves control of the mailbox, not of a session. Turning email back on is a **NotificationPreference** change.

Scoped to alert mail. Verification, password-reset, and invite mail are transactional — each answers something the recipient just did — and ignore the mute entirely.

**NotificationPreference**:
Per user and **AlertKind**, whether email and push deliver it (`emailEnabled`, `pushEnabled`); no row means both on, so only choices are stored. `NotifyService` reads the row for the alert's kind in the same query as the user and skips a switched-off **Channel**; the **Notification** row is always written, so turning a kind off never hides it from the bell. A channel without a switch (a future `sms`) is never held back. `User.alertEmailsMutedAt` (the unsubscribe) still gates email on its own, and `NotificationPreferencesService` presents the two as one state: while muted every email toggle reads off, saving every email toggle off sets the mute, and saving any back on clears it — writing the rows from what the user was shown, so a row left on from before an unsubscribe does not come back with an unrelated toggle. Served at `GET/PUT /notifications/preferences` (PUT takes only the kinds to change); a save that changes nothing writes nothing and audits nothing, one that does writes a `notification.preferences_updated` event with the before and after of the changed kinds only. `ALERT_KINDS` lives in `@vehicle-vault/shared` so the web app lists the same set.

**Channel availability**:
Whether email and push can deliver at all, apart from any kind's own switch, carried on `GET/PUT /notifications/preferences` as `channels: { email, push }`, each `{ available, reason }` with `reason` one of `not_configured` / `email_unverified` / `no_device` when unavailable. Email needs the mail transport configured (`MailService.isConfigured`) and `User.emailVerified`; push needs VAPID configured (`PushSubscriptionsService.isConfigured`) and at least one `PushSubscription` row. Computed fresh in `NotificationPreferencesService` on every read, never stored, and deliberately blind to `alertEmailsMutedAt` — the mute is a delivery choice, not an availability fact. Exists so the web app never shows a switch reading on for a channel that cannot actually deliver.

**NotifyService**:
`raise(userId, vehicleId, kind, payload, options?)` — resolves template, computes dedup key, upserts the row, and fans out to channels. The single entry point for raising any alert. The default dedup guards unread rows only, so an alert the user read can come back on the next run. Two `RaiseOptions` change that per call: `cooldownDays` skips the raise if the user has had the same alert inside the window, whether they read it, ignored it or deleted it ("same" per the template's `cooldownKey`, or the exact dedup key when it has none — see **AlertRaise**), and `inAppOnly` writes the row but skips every external **Channel**. Mechanics only — which alerts use them is the **AlertEngine**'s call. `raise` returns the row it created, the unread row that made creating one unnecessary, or null when a cooldown held the alert back.

**AlertRaise**:
The record that **NotifyService** raised an alert under a cooldown — user, vehicle, kind, dedup key and `raisedAt` — written in the same transaction as the **Notification**, and the only thing `cooldownDays` reads. Kept apart from the inbox on purpose. Deleting a Notification is a hard delete, and a cooldown that read Notification rows forgot a prompt the moment someone deleted it, so the next morning's run asked again. Rows are only ever inserted, never linked to the Notification they produced, and go only with their **User** or **Vehicle** (cascade). A raise without a cooldown writes nothing here, so every other alert still returns after a delete exactly as it did. The migration that created the table backfilled every **Cold-start prompt** already in an inbox, so deploying it reset no cooldown.
_Not_ a soft delete: marking deleted Notification rows would have meant teaching every notification query to skip them, and a deleted unread row would have kept its `notification_dedup_unread` slot and swallowed every later raise with the same key.

**ProductEvent**:
Append-only product telemetry (`modules/product-events`): `account_created`, `email_verified`, `vehicle_created`, `first_maintenance_logged`, `first_fuel_logged`, `reminder_created`, `notification_opened`. Written server-side next to the audit event of the same action, through the same client — inside its transaction when there is one — so an event never describes a rolled-back write. `properties` holds flat non-personal values only (a method, a source, a kind). User and vehicle go null on delete, so counts survive an account deletion without identifying it. The two `first_*` events are once per user **ever**: a partial unique index on `(userId, name)` is the guard, and they are written with `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`) because a plain insert tripping the index would abort the transaction and lose the record being saved. A draft maintenance record does not count until it is confirmed; a reminder rolled forward on completion is the app's doing and does not count as `reminder_created`. `notification_opened` comes only from the bell's `POST /notifications/:id/open`, with `firstOpen` separating the nudge from revisits, and carries no vehicle because a notification can outlive its vehicle. OAuth sign-ups arrive verified and never emit `email_verified`; `account_created.method` lets a funnel account for that. Read back as per-day UTC counts at the admin-only `GET /admin/product-events/summary?days=N` (1–365, default 30). Exempt from the audit-coverage safety net.
_Catalog attribution_: a sign-up from a public catalog page's "Track this vehicle" sends `catalogModel` (a model slug, validated as one) with the registration, and `account_created` gains `source: 'catalog'` and `catalogModel`; a vehicle created from that intent sends `fromCatalogIntent: true` (only `true` passes) and `vehicle_created` carries it. Neither is stored anywhere else. An OAuth sign-up gets the same `source` and `catalogModel` (with `method: <provider>`) from the model slug its **OAuth state** carried; an OAuth sign-in to an existing account records nothing.

**Rate limit**:
Per-client-IP throttling on the public auth surface, in memory (`common/rate-limit`) — the API runs as one container, so a restart resets the counters and a second instance would count separately. A route opts in with `@RateLimit(bucket)`; nothing else is limited. Buckets are policies, not counters: `login`, `register`, `mail` (anything that emails an address the caller typed) and `token`, configured as `RATE_LIMIT_<BUCKET>=requests/seconds`, off under `NODE_ENV=test`. Endpoints sharing a policy are counted separately. Login is the exception to the decorator: it is checked inside `AuthService.login`, after the email is known and before the bcrypt compare, because a guard refuses before the handler runs and a refused login must still write `auth.login_failed` (reason `rate_limited`) against the account it was aimed at. A refusal is a 429 with code `RATE_LIMITED` and a `Retry-After` header. The client is `req.ip`, which comes from `X-Forwarded-For` only when `TRUST_PROXY` is set — required behind the production proxy, or every visitor shares the proxy's address and one limit. Production wants `loopback, linklocal, uniquelocal`, not `true`: Cloudflare appends the real client IP after whatever the client sent, so trusting every hop would take a spoofable leftmost entry.

**Cold-start prompt**:
The two alerts that ask rather than tell: `tyre-uninspected` with reason `untracked` (no tyres on file) and vehicle-scope `service-baseline-unknown` (no service history at all). The **AlertEngine** raises them through `raisePrompt`, which adds three rules the condition alerts never get: nothing at all for a vehicle created in the last 7 days (it is still being set up); a 90-day cooldown per vehicle and prompt, counted from when it was raised, whether it was read, ignored or deleted; and in-app only for a recipient with no audited action in 60 days. Dormancy counts any **AuditEvent** the user is actor on except `auth.login_failed`, which is recorded against the account it targeted — so a stranger guessing passwords cannot keep an idle account looking active. It is judged per recipient, so fanning alerts out to every **VehicleMember** decides it separately for each. The cooldown reads **AlertRaise** rather than the inbox, so deleting a prompt — a stronger "go away" than reading it — keeps it quiet for the rest of its 90 days instead of clearing its history.

**AlertEngine** (`MaintenanceAlertService`):
The cron orchestrator that runs per-vehicle, reads current predicted odometer (`VehicleInsightsService`), and calls **NotifyService.raise** for each crossed threshold (intervals from `MaintenanceIntervalResolver`, reminders within 500 km of `dueOdometer` or 7 days of `dueDate`, documents expiring within 7 days via `VehicleDocumentsService.findExpiring`, tyre verdicts from `TyresService.getAlertState`, last-done odometers from **ServiceBaseline** rows loaded with the vehicle). Owns _when_ to alert, not _what_ the alert looks like.

Raises to the vehicle's **VehicleMember** rows, loaded in the same vehicle query, not to the legacy `Vehicle.userId` (kept only as a fallback for a vehicle with no member rows). Every member — owner, editor, viewer — gets the alerts about the vehicle's state. The two kinds that ask the reader to log something, `service-baseline-unknown` and `tyre-uninspected` in all their variants, go to the owner and editors only: a viewer cannot answer them. Each member's copy is a separate `raise`, so dedup, cooldowns, dormancy and channel gating all apply per member. The reads that find what to alert about (`getOdometerInsights`, `findExpiring`, `findExpiringWarranties`, `getAlertState`) still pass the owner column, since they are about the vehicle, not the reader.

**Two-wheeler service intervals**:
`MaintenanceIntervalResolver` (`modules/vehicles`) resolves a separate default interval table for `VehicleType.Motorcycle` — which covers scooters too; there is no separate scooter type — instead of gating a handful of categories off the four-wheeler table. Two-wheelers never get `tyre_rotation`, `wheel_alignment` or `timing_belt`, and `chain_service`/`coolant` are gated on the linked variant's `VehicleCatalogVariantSpec.driveType`/`coolingType` text (a substring match, e.g. "chain", "liquid"), read with one extra query only for a motorcycle-typed, catalog-linked vehicle. Neither is guessed when the fact isn't recorded — most two-wheeler specs currently have no `driveType` at all, so `chain_service` stays off until that's backfilled. Two-wheelers also get `spark_plug` (every non-electric one) and `cvt_belt` (only when the variant's `transmission` reads as a belt CVT: "CVT" or "Automatic", never DCT/AMT), both by distance only because the makers' schedules state no time limit; a car gets neither, even from a variant row.

**Tyre observation**:
The last time anyone had eyes on a **Tyre** — its newest **TyreInspection**, or its `fittedDate`/`fittedOdometer` when it has never been measured. `TyresService.getAlertState` reports the _oldest_ observation across a vehicle's road tyres (the spare is graded but excluded, since it covers none of the vehicle's mileage), and the **AlertEngine** raises `tyre-uninspected` once that observation is older than `TYRE_INSPECTION_INTERVAL_KM` / `_MONTHS`. The distinction this encodes: a tyre nobody has measured is **unknown**, not healthy, and unknown is a thing to say out loud rather than a reason to stay quiet.

**ServiceBaseline**:
What was known about one **MaintenanceCategory** on a **Vehicle** when it entered the vault — an odometer reading, a date, or an explicit `unknown`. Unique per `[vehicleId, category]`; a CHECK constraint keeps `known` carrying a figure and `unknown` carrying none.

Three states, not two, and the third is the absence of a row:

| State                          | Engine behaviour                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------- |
| A **MaintenanceRecord** exists | measured from the record — always wins over a baseline, which was a recollection |
| `known` with an odometer       | measured from the baseline                                                       |
| `known` with only a date       | no km alerting; the forecast owns month-based intervals                          |
| `unknown`                      | raises `service-baseline-unknown`, scope `category`                              |
| **no row**                     | the historical fallback: measured from `Vehicle.odometer`                        |

That last row is the behaviour this table exists to retire, and it is kept deliberately. Before **ServiceBaseline**, a category with no record was measured from the odometer at the moment the vehicle was added — silently asserting everything had just been done, so a bike added at 40 000 km was treated as having had its brake pads changed at 40 000 km. Every vehicle predating the table is in the no-row state, and reading it as `unknown` would greet each existing garage with one notification per service category. Users move out of it by answering, through `PUT /vehicles/:vehicleId/service-baseline`.
_Not_ a **MaintenanceRecord**: a baseline is what someone remembers, carries no cost, no line items and no attachment, and never contributes to ₹/km.

**Service intervals** — `vehicles/maintenance-interval.resolver.ts` is the single source of truth for "how often does this vehicle need X". It gates categories by vehicle type and fuel, and prefers per-variant `ServiceInterval` rows over its default table. `MaintenanceAlertService` and `MaintenanceForecastService` both consume it, and it is served to clients at `GET /vehicles/:vehicleId/intervals` so the web app never restates an interval locally — a client that picks its own number will disagree with the alert engine about the same vehicle.
_Caution_: `reminders/service-schedule-catalog.ts` still carries its own generic intervals for the reminder-suggestion flow, and some of its figures differ from the resolver's. It is scoped to "what reminders could I create", not "is this service due", but the two should be reconciled. Its `tyre_inspection` item is the exception that reads from shared constants (`TYRE_INSPECTION_INTERVAL_KM` / `_MONTHS`) rather than restating a number, because the **AlertEngine** grades the same cadence and the two must not drift.

**Token**:
A credential issued to a **User** for a specific purpose: email verification, password reset, or refresh session. **TokenService** owns issue/consume/rotate/revoke lifecycle for all purposes, regardless of whether the bits are a JWT (refresh) or a SHA-256 hash of random bytes (verification, reset). Timing-safe comparisons. See ADR-0002.

**Email verification deadline**:
A new password account may use the app unverified for `EMAIL_VERIFICATION_GRACE_DAYS` (7) from `createdAt` (`modules/auth/email-verification-deadline.ts`). `AuthUser.emailVerificationDueAt` carries the moment, or null when there is nothing to wait for: the address is verified, or it is the `@oauth.local` placeholder an OAuth sign-in without an email gets. The API itself does not gate on verification — the web app turns the deadline into a banner and then a wall, and alert email waits for verification regardless.

**OAuth state** (`modules/auth/oauth-state.ts`):
The `state` parameter of Google and GitHub sign-in, a passport-oauth2 state store on both strategies. Beginning at `GET /auth/oauth/{provider}?catalogModel=` signs `{provider, nonce, expiry (10 min), model slug?}` with an HMAC key derived from `JWT_SECRET` and sets the nonce as an HttpOnly, SameSite=Lax cookie (`vv_oauth_state`) on the provider's callback path, Secure when the callback URL is https. The callback is accepted only when the signature, provider, expiry and cookie all agree, checked before the code is exchanged, so the slug cannot be forged and a callback minted in another browser (login CSRF) is refused. The slug is checked against `CATALOG_SLUG_PATTERN` going in and coming out; an invalid one is dropped, never an error. No session store. The callback routes use `OAuthCallbackGuard`, which turns a cancel (`oauth_cancelled`), a refused state (`oauth_state_invalid`) or a provider error (`oauth_failed`) into a redirect to the web app's `#error=` instead of a JSON 401 on the API's own origin. The strategies' `validate` returns the profile rather than calling `done`: calling both ran passport's callback twice and the second (failed) call overwrote `authInfo`, where the verified state arrives.

**OAuth return path**:
Beginning also takes `next`, the web app's return path (where its route guard was taking a signed-out visitor). It is kept only when `toSafeReturnPath` (shared package) accepts it as a same-origin path, signed into the state as `r` beside the model slug, checked again when the state is read, and handed back as `next` in the callback fragment, on success and on a failure after the state verified, so the web app can go there after signing in. A bad value is dropped, never refused. A cancel at the provider never verifies the state, so it comes back without one.

**Account deletion** (`modules/users/account-deletion.service.ts`):
`AccountDeletionService.deleteAccount(userId)` is the one way an account goes. Deleting the **User** row cascades through its owned vehicles (and every record, reminder, document and attachment row under them), memberships, invites, notifications and preferences; **AuditEvent** and **ProductEvent** rows are set to null. The service adds what a cascade cannot: it anonymises the audit trail in the same transaction (`AuditService.anonymiseForUser`: rows about their own data lose the owner link and every payload value; rows where they acted lose the actor, IP and user agent, but keep the owner and payload when the data is someone else's), writes an ownerless `auth.account_deleted` event, and then removes the files — every attachment on the owned vehicles, plus anything left under the uploader prefixes `attachments/<userId>/` and `claim-attachments/<userId>/` that no row points at. A vehicle shared with anyone else is refused: ownership has to move first. `plan(userId)` reports all of this without changing anything. There is no endpoint yet; `src/scripts/purge-test-accounts.ts` drives it (dry run by default, `--execute --ids=` for reviewed ids only) and runs inside the API container with `node dist/src/scripts/purge-test-accounts.js`.

**AuditEvent**:
An immutable record of one happened-thing in the system. Two flavours: a **mutation** against a tracked resource or an **auth event**. Dotted `action` string (`vehicle.updated`, `auth.login_failed`), optional `actorUserId`, polymorphic no-FK resource reference (`resourceType` enum + `resourceId`), diff payload (`before`/`after`/`changedFields`, PII-redacted). Written **inside the same transaction** as the mutation via `auditService.track(tx, …)`; a dev/CI safety net in `PrismaService.$transaction` throws `AuditCoverageError` when an audited mutation emits no event. Survives deletion of subject and actor. Rendered to end users as "Activity". See ADR-0004.
_Not_ a **Notification**; not a log line.

**Actor**:
The **User** who caused an **AuditEvent**, or `null` when no user can be resolved.

**DocumentExtraction**:
Structured data pulled from a user-uploaded file (image or PDF) by an AI provider. Has an **ExtractionKind**, an optional `confidence` score, a `provider` tag (`gemini` today via `GeminiExtractionProvider`, JSON-schema-constrained), and optionally a persisted row (e.g. `AttachmentExtraction`) kept for replay/audit. Output is a draft, never an authoritative record — the human always confirms via a form before the target resource is persisted. **Fill in from photo** writes into a confirmed record, but only its blanks, and only after the person has seen the list. See ADR-0005.
_Not_ "OCR" — the provider reasons over the document. _Not_ "scan" — UI verb only.

**ExtractionKind**:
Discriminator for what shape the extracted JSON takes and which target resource the draft hydrates. Five today: `fuel_receipt`, `maintenance_invoice`, `insurance_policy`, `claim_document`, `loan_document`. Specs (schema + prompt + normalize) are co-located with their consumer module and register **imperatively** via `ExtractionRegistry.register()` in each module's `onModuleInit` — _not_ a DI multi-provider, despite ADR-0005's wording (known doc↔code divergence).

**Catalog**:
The India make → model → generation → variant → offering reference dataset (`VehicleCatalog*` models), with ~90-field variant specs, alias tables for fuzzy matching, and versioned **ImportRuns** with sha256-hashed snapshots. Fed by ~35 per-brand source snapshots under `prisma/catalog-import/sources/` (CarWale-scraped), imported via `catalog:import:*` scripts, curated via audit/backfill/pseudo-variant-cleanup tooling and an admin review UI. **VehicleCatalogLinkerService** fuzzy-links user Vehicles to variants from make, model, year, type and fuel — it never reads `Vehicle.variant`, and settles for a generation link when more than one variant fits. That is what lets `Vehicle.variant` be optional: a vehicle with no trim named still resolves service intervals through its generation, and only the per-variant spec sheet is unavailable until someone names it.

**Public catalog**:
The **Catalog** as strangers see it, with no sign-in (`public-catalog` module, `@Public`, rate-limited under the loose `catalog` bucket, `Cache-Control: public`). `PublicCatalogService` owns what is publishable (India market, a variant with at least one offering, a type with a public segment: car/SUV/van under `cars`, motorcycle under `bikes`, no trucks or `other`) and the spec allow-list `PUBLIC_SPEC_FIELDS`: factual columns picked by name, so `sourceName`/`sourceUrl`, free-text feature lists and import-run data never leave it, and a new spec column stays private until listed. A page's service schedule comes from `MaintenanceIntervalResolver.resolveForVariant`, the same resolution a tracked vehicle gets, and is labelled `variant` or `typical` by whether any interval came from the variant's own rows. Ended ("archived") offerings stay public as history: a page for a variant no longer sold is still a page its owners search for.

**Public catalog index**:
`GET /public-catalog/index` lists every publishable variant (segment, names and slugs down to the variant, newest `updatedAt`) in one unpaginated response, and `GET /public-catalog/variant-pages?page&pageSize` (at most `PUBLIC_CATALOG_VARIANT_PAGE_BATCH_MAX`, 200) returns the same variant page payloads the per-variant route does, in the same `id` order. They exist for the web build's prerender, which would otherwise need one request per variant and run into the `catalog` rate limit; both share `PublicCatalogService`'s publishable rule with the slug lookup.

**Page-quality gate**:
`public-catalog/page-quality.ts`, pure: whether a public page has enough facts to be worth indexing. A variant passes with a spec row holding at least `MIN_FILLED_PUBLIC_SPEC_FIELDS` (10) filled public fields, a claimed mileage (`mileageCombined`) and engine data (`engineCc` or `powerPs`); an EV, told apart by the fuel of its newest offering (never by having a `rangeKm`, which on a bike is its tank range), needs a claimed `rangeKm` and motor data (`motorKw` or `powerPs`) instead. `evaluateVariantPageQuality` returns `{indexable, reasons}`; the variant page payload and each index entry carry `indexable`, computed by the same call so they cannot disagree (the prerender fails if they do). `evaluateModelPageQuality` (any variant indexable) judges model pages. The web build's indexing flag overrides the gate; with it off, nothing is indexed whatever the gate says.

**Public model page**:
`GET /public-catalog/:segment/:make/:model` (and in bulk, by address, `GET /public-catalog/model-pages?page&pageSize`, at most `PUBLIC_CATALOG_MODEL_PAGE_BATCH_MAX`, 100) returns every publishable variant at a model _address_, grouped by generation (current first, then most recently ended, then most recently started), variants on sale first, then by name. An address can span model rows under more than one make row (Hyundai is a car and an SUV make with one slug), so pages group by address, a generation or variant slug seen twice listed once (first row by `id`). A model has no specs or schedule of its own: the page shows its **representative** variant's (current generation, on sale, passing the page-quality gate, newest offering, most facts, then name), and resolves only that variant's schedule. `indexable` is `evaluateModelPageQuality` over the listed variants.

**Public make and browse pages**:
`GET /public-catalog/:segment` (every make with public pages there, by name, with its model count; an empty list, not a 404, for a segment with nothing) and `GET /public-catalog/:segment/:make` (its models, on sale first, then by name, each with its variant count, fuels and years; `indexable` when any variant under it is, `updatedAt` the newest). They are summaries of the **Public catalog index**, built by `buildPublicCatalogBrowsePage` and `buildPublicCatalogMakePage` in `@vehicle-vault/shared` over the index entries of that segment or make, the same functions the web build's prerender runs over the whole index, so the two cannot disagree and the prerender needs no request per make. Like model pages they group by address: `/cars/hyundai` lists the models of Hyundai's car and SUV rows, and a variant address seen twice counts once (first row by `id`). Index entries carry each variant's fuels, first and last years and whether it is on sale for this. `:segment` is declared after the fixed one-segment routes (`index`, `variant-pages`, `model-pages`), so those keep their paths.

**Generation merge**:
Sources overlap: an official-site snapshot names a model's real current generation with years ("Amaze (2024 refresh)"), the CarWale scrape files the same car under a yearless "(current)" placeholder, and the curated seed adds a yearless "lineup", sometimes under another make row of the same address (CarWale's car-type Honda Elevate vs Honda's SUV row). `catalog:merge-duplicate-generations` (plan: `vehicle-catalog/generation-merge-plan.ts`, dry run first) folds placeholders into the one real current generation per address, skips addresses with two real current generations (TVS Jupiter 110/125), and keeps each absorbed name as a generation alias. `catalog-import/generation-redirects.ts` then sends a re-import of the old name to the absorbing generation (upsert) and files it there for the import review, so archive-missing never ends a merged variant's offerings.

**Trim merge**:
CarWale names some trims differently from the official sources, so one generation could hold the same trim twice: model-prefixed ("3XO AX5" beside "AX5") or a bare parent beside its detailed children (Honda's "V" beside "V | Petrol | Manual"). `catalog:merge-near-duplicate-trims` (plan: `vehicle-catalog/trim-merge-plan.ts`) folds each into the survivor with `catalog-import/variant-fold.ts`, the same fold the generation merge uses, and keeps the folded name as a variant alias. Names that only share a prefix ("SX" and "SX (O)") are different trims and stay. Imports and the import review redirect a folded name to its survivor (`findVariantRedirect`), and an import writing onto a survivor skips an offering another source already gives for that fuel mix.

**Trim names**:
CarWale repeats part of the model name at the start of many trim names ("Liva GX" in the Toyota Etios Liva, "7 Premium" in the BYD eMax 7). `catalog:strip-model-name-from-trims` (plan: `planTrimRenames` in `vehicle-catalog/trim-merge-plan.ts`) drops it ("GX", "Premium") and keeps the old name as a variant alias, so imports and the import review find the renamed trim (`findVariantRedirect`). A trim whose shortened name already exists is a duplicate for `catalog:merge-near-duplicate-trims`, run first, and is left alone.

**MaintenancePartCatalog**:
A **global, cross-user** self-learning table mapping normalized part names → suggested `MaintenanceCategory`, harvested from user line items. Powers category suggestion and part search. Not user-scoped (mild data-leakage consideration for part numbers).

## Module map

auth (register/login/refresh/OAuth/verify/reset), users, admin (user directory, force-logout, admin-email role reconciliation on boot), vehicles (CRUD, insights/forecast, catalog linking), vehicle-sharing (members/invites/transfer), vehicle-catalog (browse + import-run admin), public-catalog (signed-out catalog pages), maintenance (+ drafts, bulk, CSV), maintenance-parts, reminders (+ service-schedule), service-baseline (per-category history capture + coverage), fuel-logs (+ scan), history (the garage timeline), vehicle-documents (insurance/warranty adapters + scan), claims (+ claim-attachments), vehicle-loans (+ amortization, scan), accessories (purchases + warranty expiry), attachments (polymorphic, extract/apply/reconciliation), notifications (NotifyService + AlertEngine + EmailChannel), audit, analytics (cost-split/cost-trend/TCO), dashboard, reports (service-history + resale PDFs), exports (account dump), extraction (`@Global` engine), health.

## Relationships

- A **Vehicle** has many **VehicleMembers**, **VehicleDocuments**, **MaintenanceRecords**, **Reminders**, **FuelLogs**, **Claims**, **VehicleLoans**, **Tyres**, **Accessories**, **ServiceBaselines**.
- The **AlertEngine** reads **ServiceBaseline** rows through the vehicle's own `include` rather than a service call — it runs once per vehicle across the whole table, and a baseline is a small child row of the vehicle already being read. `ServiceBaselineService.getCoverage` serves the same facts to clients, deliberately matching the engine's record lookup (confirmed only, ordered by odometer) so the screen explaining a reminder cannot disagree with the reminder.
- The **AlertEngine** reads **VehicleDocumentsService.findExpiring(withinDays)** (adapters implement `findExpiringBetween`) to produce expiry **Notifications**. It does not query document tables directly.
- The **AlertEngine** also reads **AccessoriesService.findExpiringWarranties(withinDays)** for the `accessory-warranty-expiring` kind. Accessory warranties raise **Notifications**, never **Reminders** — `Reminder` carries no pointer to a source record, so the notification is the only thing that can say which accessory it is about.
- The **AlertEngine** skips `reminder-due` / `reminder-overdue` for a **Reminder** carrying the `tyre_inspection` catalog slug. Both signals would otherwise nag about one thing and disagree about it: a reminder goes overdue when nobody ticked a box, `tyre-uninspected` when nobody actually looked, and only the second is true about the tyres. Someone who inspects and forgets to tick is left alone; someone who ticks without inspecting is not.
- The **AlertEngine** reads **TyresService.getAlertState(userId, vehicleId)** for the three tyre kinds. Grading stays in **TyreConditionResolver** and reaches the notification as a rendered verdict, so the same numbers back the alert and the vehicle page — the engine never re-derives "is this tyre finished". Graded against `Vehicle.odometer`, not the predicted reading: a forecast must not be what declares a tyre worn.
- A **MaintenanceRecord** with `status: draft` is not evidence a service happened — it is a **DocumentExtraction** hydrated into a row that nobody has confirmed, and `AttachmentsService.applyExtraction` writes the invoice's `totalCost` onto it while leaving it a draft. Everything that answers "what was done" or "what was spent" therefore reads confirmed rows only: **AlertEngine**, `ServiceBaselineService.getCoverage`, **MaintenanceForecastService**, both **reports** PDFs, and all three **analytics** aggregations (including the claim joins netted against them, or the maintenance bucket would drop below what was spent), plus the dashboard's per-vehicle last service and its `hasSpend` switch. Three call sites deliberately read every row and say so in a comment: **VehicleInsightsService** (a draft's odometer is a real reading, and the question is mileage, not service), vehicle deletion (drafts own attachments that must be removed from storage), and **AuditQueryService** (the trail must show what happened to a draft too). The dashboard's `recentMaintenance` lists drafts as well, each carrying its `status`, so the web can mark one for confirming rather than drop it from sight.
- `POST /attachments/:attachmentId/extract` reads a file only as a `maintenance_invoice`, which nothing but a **MaintenanceRecord** can take (`applyExtraction` and fill refuse any other owner). So it answers 400 for a **VehicleDocument**'s or **VehicleLoan**'s file, whatever the caller's role, before the file is downloaded or the provider called. Those are read as their own **ExtractionKind** from a fresh upload: `POST /vehicles/:vehicleId/documents/scan` and `POST /vehicle-loans/scan`.
- An **Attachment** has exactly one owner of five — **MaintenanceRecord**, **InsurancePolicy**, **Warranty**, **Claim**, or **VehicleLoan** — enforced by CHECK constraint `attachment_owner_exclusive`.
- Running a **DocumentExtraction** over a **MaintenanceRecord**'s files is an edit, not a read: both extract routes assert editor on the vehicle before the file is downloaded. Any member may open the file, but an extraction spends a provider call and overwrites the stored `AttachmentExtraction` row — and only an editor can apply what comes back.

## Flagged ambiguities

- "Policy" was used to mean **InsurancePolicy** (Prisma model) and any **VehicleDocument**. Resolved: **InsurancePolicy** is the storage row for `kind=insurance`; the domain term is **VehicleDocument**.
- "OCR" / "scan" / "extraction" were used interchangeably. Resolved: domain term is **DocumentExtraction**; "scan" reserved for UI verbs; "OCR" deprecated.
- `Vehicle.userId` vs **VehicleMember**: dual ownership representation. Members are authoritative for access; `userId` remains for the registration-number unique and cascade. Candidate for consolidation.
- ADR-0005 describes spec registration as a DI multi-provider; the implementation is an imperative registry. Reconcile when next touching extraction.
